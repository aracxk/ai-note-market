# 厳格コードレビュー・プロトコル (Strict Code Review Protocol)

本スキルは、AI-Note Market におけるコード品質、アーキテクチャ規約、ドメインの純粋性を担保するための標準コードレビュー・実行エンジンです。
誰が実行しても常に同じ判定基準・チェック項目・出力フォーマットで客観的なレビューを実施します。

---

## 1. レビュー実行手順 (Execution Steps)

レビュー依頼を受けたエージェントは、以下の手順を順番に実行すること。

1. **静的検証・テストの実行**:
   - `npm run typecheck` を実行し、型エラーが 0 件であることを確認する。
   - `npm run test` を実行し、全単体テストが All Green であることを確認する。
   - `npx @biomejs/biome check` を実行し、Error, Warn, Info などの警告・提案が一切出力されない（波線ゼロの）状態であることを確認する。
2. **差分・対象コードの精査**:
   - `git status` および `git diff`（または対象ファイル群）を確認し、変更内容を特定する。
3. **16項目のチェックリストによる全件照合**:
   - 以下の「2. レビュー観点チェックリスト」の全項目を照合し、合否（合格 / 要修正 / 改善提案）を判定する。
4. **標準レビューレポートのチャット表示**:
   - 以下の「3. 標準レビューレポート出力フォーマット」に従い、まずチャット上でユーザーにレビュー結果を提示する。
5. **ユーザーへの確認と PR へのレビュー投稿**:
   - 「このレビュー内容で PR にコメント投稿してよろしいでしょうか？」と確認を行い、ユーザーの承認を得てから GitHub PR へレビューコメントを投稿する。

## 2. レビュー観点チェックリスト (15 Items)

### カテゴリA: ドメイン層の純粋性とカプセル化
- [ ] **A-1: 外部依存ゼロ**: ドメイン層（`src/**/domain/`）に、React, Next.js, Prisma, 外部HTTP等のライブラリ import が一切存在しないか？（純粋な TypeScript であること）
- [ ] **A-2: ファクトリによるカプセル化**: コンストラクタが `private` または `protected` に保護され、`create()`, `reconstruct()` 等の静的ファクトリメソッド経由でのみ生成可能か？
- [ ] **A-3: 基底クラスの適切な継承**: 値オブジェクトは `extends ValueObject`（`equals` 実装）、エンティティは `extends Entity<ID>`（ID同一性判定）を正しく継承しているか？

### カテゴリB: メモリ最適化とオブジェクト設計
- [ ] **B-1: Flyweight キャッシュの適用**: 0円（無料）や固定ステータス、全組み合わせカテゴリ等の頻出インスタンスが事前にキャッシュ・再利用されているか？
- [ ] **B-2: 参照同一性テストの存在**: キャッシュ対象のクラスに対して `expect(a).toBe(b)` による参照一致テストが存在するか？
- [ ] **B-3: 完全不変性（Immutable）**: 値オブジェクトのプロパティが `readonly` で保護され、安易な Setter が存在しないか？

### カテゴリC: エラー設計と型安全
- [ ] **C-1: Result 型によるハンドリング**: ドメイン層の不正値や状態遷移エラーにおいて、`throw` ではなく `Result.err(new CustomDomainError(...))` が型安全に返されているか？
- [ ] **C-2: エラーコードの一元管理**: すべてのドメインエラーが `DomainErrorCode.ts` の定数（機械判別可能）を参照しているか？
- [ ] **C-3: 安全なアンラップ**: テストコード等で `result.value!` のような危険な参照を避け、型ガードや安全なヘルパーが使われているか？

### カテゴリD: 単体テストの網羅性と品質
- [ ] **D-1: AAA パターンの徹底**: Arrange（準備）/ Act（実行）/ Assert（検証）の構造で記述されているか？
- [ ] **D-2: 境界値・異常系の網羅**: 文字数・価格の上限・下限・キワ、小数、負数、空文字、無効ステータス遷移のテストが含まれているか？
- [ ] **D-3: テストの可読性と実行速度**: テスト名が日本語の仕様書として読め、モック不要で数十ミリ秒以内に完了するか？

### カテゴリE: ドキュメント・規約・ADR同期
- [ ] **E-1: 絵文字の不使用**: ソースコード、コメント、ドキュメント、コミットメッセージに絵文字が一切含まれていないか？
- [ ] **E-2: ユビキタス言語の完全一致**: 会話、仕様書（`docs/02-domain-models/`）、コード上のプロパティ名（`authorId`, `buyerId` 等）にブレがないか？
- [ ] **E-3: ADR の起票と記録**: 新しい設計方針やルール改定に対する「理由（Why）」が `docs/03-adr/` に記録されているか？
- [ ] **E-4: Lint警告のゼロ化**: Biome からの提案 (info) や警告 (warn) が一切無視されておらず、コードベースに波線が残っていないか？（※警告が存在する場合、単にコードを修正するよう指摘するだけでなく、「コードを修正すべきか、それとも `biome.json` でこのルールを `off` に設定して波線を消すべきか」の判断をメインAIとユーザーに委ねる文言をレポートに含めること）

## 3. 標準レビューレポート出力フォーマット

レビュー結果は必ず以下の Markdown フォーマットで出力すること。

```markdown
# 厳格コードレビュー結果 (Strict Code Review Report)

- **対象ブランチ / 差分**: `...`
- **型チェック (tsc)**: 合格 (エラー 0 件) / 不合格
- **単体テスト (Vitest)**: 合格 (xx 件 All Green, xx ms) / 不合格
- **総合判定**: 【承認 (Approve)】または【要修正 (Changes Requested)】
```
