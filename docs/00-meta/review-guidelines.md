# コードレビュー運用指針 (Code Review Guidelines)

- **カテゴリ**: メタ・開発方針 (`docs/00-meta/`)
- **テーマ**: 個人開発におけるAI客観的コードレビュー体制とチェックリスト

---

## 1. 背景と課題：個人開発におけるAIセルフレビューの限界

個人開発において、コードを実装した同一チャットセッションのAIに「レビューしてください」と依頼すると、以下の問題（バイアス）が発生する：

1. **コンテキスト汚染**: 直前までの実装意図や前提に引っ張られ、設計の抜け漏れやエッジケースの盲点に気付きにくい。
2. **過度の肯定（Yes-man化）**: 自分が書いた直後のコードに対して批判的な視点が鈍る。

---

## 2. 解決策：マイルストーン単位の「コンテキスト分離レビュー」

開発テンポを維持しつつ、プロフェッショナルな品質を担保するため、以下の運用を行う。

```text
[ 普段の実装中 ] ─── main ブランチで対話しつつ高速に実装・テストを進める
       │
       ▼ (マイルストーン到達：例 Phase 1 ドメイン層完成時)
[ コンテキスト分離レビュー ]
  └─ 新しいチャットセッション（または別AIツール / Subagent）を起動し、
     過去の文脈を一切持たない「初見のレビュアー」として厳格に差分（git diff）を精査させる。
```

---

## 3. レビュアーへの指示プロンプト雛形

新セッションまたは別AIにレビューを依頼する際は、以下のプロンプトを使用する。

```text
【客観的コードレビュー依頼プロンプト】
あなたは厳格なシニアアーキテクト兼レビュアーです。
本リポジトリの規約（docs/00-meta/conventions.md）に基づき、
今回実装された以下のコード（git diff / ファイル群）を厳格にレビューしてください。

【重点チェック項目】
1. ドメインの純粋性（外部依存の混入がないか）
2. 不変条件の保護（不正値生成が物理的に不可能か）
3. メモリ最適化（頻出値の Flyweight キャッシュが適用されているか）
4. 単体テストの網羅性（境界値テスト、参照一致 toBe テストがあるか）
5. エラー設計（Result 型と一意なドメインエラーコードが使われているか）
6. 命名と規約（絵文字不使用、日本語コミット等）

妥協せず、改善点や潜在的バグを具体的に指摘してください。
```

---

## 4. レビュー観点チェックリスト (Review Checklist)

レビュアーおよび開発者は、マイルストーン完了時に以下の項目をすべてパスしていることを確認する。

### ① ドメイン層の純粋性とカプセル化
- [ ] ドメイン層（`src/**/domain/`）に、Next.js、React、DBライブラリ等の外部 import が一切存在しないこと（純粋な TypeScript であること）。
- [ ] コンストラクタが `private` になっており、`create()` などの静的ファクトリメソッド経由でのみ生成可能であること。
- [ ] プロパティが `readonly` で保護され、オブジェクトが完全不変（Immutable）であること。

### ② メモリ・パフォーマンス最適化
- [ ] 0円（無料）や特定ステータスなど、頻出する固定値・デフォルト値に Flyweight パターン（インスタンスの事前キャッシュ・使い回し）が適用されていること。
- [ ] キャッシュされた値オブジェクトについて、`expect(a).toBe(b)` による参照一致（同一インスタンス返却）テストが存在すること。

### ③ エラーハンドリング
- [ ] 想定内のビジネスルール違反が `throw` ではなく `Result.err(new CustomDomainError(...))` で型安全に返されていること。
- [ ] 各ドメインエラークラスが一意な `code`（機械判別用定数）を保持していること。

### ④ 単体テストの品質
- [ ] AAAパターン（Arrange / Act / Assert）に沿って構造化されていること。
- [ ] 正常系だけでなく、境界値（上限・下限・キワ）や異常系（小数、負数、空文字等）が網羅されていること。
- [ ] テスト名が仕様（ビジネスルール）として自然な日本語で読めること。

### ⑤ ドキュメントと規約
- [ ] ソースコード、コメント、ドキュメントに絵文字が含まれていないこと。
- [ ] 定数やビジネスルールの変更時、JSDoc、インラインコメント、仕様書の全件Grep検証が実施され、古い数値や記述の不整合がゼロであることを確認したか？
- [ ] 今回の設計判断やルール変更に対する「理由（Why）」が `docs/03-adr/` に起票・記録されているか？
- [ ] `docs/` 配下の該当仕様書および学習ログが最新状態に更新されていること。
