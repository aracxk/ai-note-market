# Step 4: CI/CDの役割分担とローカル環境（Husky/Biome）の最適化

本ステップでは、ドメイン層の構築を一時的に離れ、チーム開発における「安全網（CI/CD）」と「開発体験（DX）」の両立について議論し、環境を整備しました。

## 1. なぜ「重い処理」と「軽い処理」を分けるのか？

CI/CDを構築する上で最も陥りがちなアンチパターンは、「コミットする前に（ローカルで）すべてのテストと型チェックを走らせる」という設定です。
これを行うと、1回の `git commit` に数秒から数十秒待たされるようになり、開発のテンポ（Flow）が著しく阻害されます。結果として、開発者は `--no-verify` を使ってチェックをバイパスするようになり、ルール自体が形骸化してしまいます。

### 解決策（役割分担）
- **Push後（GitHub Actions / クラウド）**: 
  - `npm run typecheck` や `npm run test` などの重い処理を実行。
  - メインブランチを保護するための「最後の砦」として機能させる。
- **Commit直前（Husky + lint-staged / ローカル）**:
  - `biome check --write` などの「超高速（数ミリ秒）な静的解析とフォーマット」のみを実行。
  - 開発者が一切のストレスを感じることなく、裏側で自動的にコードを綺麗にする。

## 2. ESLint/Prettier から Biome への移行

従来のモダンフロントエンドでは `ESLint` と `Prettier` の組み合わせが定番でしたが、設定の競合や動作の重さが課題でした。
本プロジェクトでは Rust 製の **Biome** を採用し、以下のメリットを享受しています。

- **設定ファイルの単一化**: `biome.json` だけで Lint と Format の両方を管理。
- **爆速な実行速度**: プロジェクト全体のフォーマットが約10msで完了し、Huskyの pre-commit フックに挟んでも人間には感知できない速度で完了する。
- **モダンなデフォルト設定**: アクセシビリティ等の観点から推奨される「タブインデント」を標準採用（郷に入っては郷に従う）。

## 3. Next.js (Vercel) のビルドの罠とプレゼンテーション層

DDD や Clean Architecture においてドメイン層（`src/features/` など）から作り始めると、Next.js 特有の「画面ファイルが存在しないとビルド（`next build`）が落ちる」という罠に直面します。

```text
Error: > Couldn't find any `pages` or `app` directory. Please create one under the project root
```
この仕様により、Vercel のデプロイや `next lint` も動作しません。これを回避するため、ドメイン層の構築フェーズであっても最低限のダミーファイル（`src/app/page.tsx`, `layout.tsx`）を配置し、Vercel のビルドを成功（緑色）状態に保つ手法を取りました。

## 4. Antigravity エージェントルールのネイティブ化 (YAGNI原則)

汎用的な `CLAUDE.md` や単なるテキストの `agent.md` は、AI が会話の文脈によって読み落としてしまう（勝手にコミットしてしまう等の暴走）リスクがありました。
本プロジェクトでは「必要になるまで作らない（YAGNI）」の精神に基づき、使わない `CLAUDE.md` を思い切って削除しました。代わりに、Antigravity（AI自身）が会話開始時に必ず強制的に読み込む専用ディレクトリ `.agents/rules/` にルールを移行し、システムレベルでの行動制御を確立しました。
