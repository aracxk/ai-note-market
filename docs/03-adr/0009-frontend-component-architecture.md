# ADR 0009: フロントエンドコンポーネントアーキテクチャとUIライブラリの選定

## 1. 背景と目的 (Context)
Phase 5 にて、堅牢に構築されたDDD（ドメイン層）およびCQRS（クエリ層）に対する最外層として、Next.js App Routerを用いたPresentation（UI）層を実装する。
本プロジェクトの目的は「最適な設計思想の学習」であるため、フロントエンド側においても場当たり的なUI実装を避け、保守性が高く、バックエンドのクリーンアーキテクチャと調和するモダンなコンポーネント配置ルールを策定する必要がある。
また、複数のUIライブラリ（shadcn, Magic UI 等）の混在や、状態管理（Form, データフェッチ）の無秩序な導入によるスパゲッティ化を未然に防ぐための厳格なルールも同時に定義する。

## 2. 決定事項 (Decision)

### 2.1 UIライブラリ群の採用と名前空間（Namespace）の分離
ブラックボックスなnpmパッケージへの依存を避け、「所有するUI」の哲学を持つライブラリ群を採用する。ただし、これらが1つのフォルダ内で衝突・スパゲッティ化するのを防ぐため、**提供元ごとにディレクトリを完全に分離（名前空間化）**する。

- `src/components/ui/` : 公式 `shadcn/ui` の標準コンポーネント（Button, Dialog 等。CLIが自動配置する場所）
- `src/components/magicui/` : `Magic UI` のリッチアニメーションコンポーネント
- `src/components/aceternity/` : `Aceternity UI` の特殊エフェクトコンポーネント

※これらのディレクトリ内のファイルはすべて「純粋なUI部品」であり、ドメイン知識（`src/features/`）をインポートしてはならない。

### 2.2 フォーム・状態管理アーキテクチャ（RHF vs TanStack）
フロントエンドにおける状態管理とフォーム処理の方針を以下のように一本化し、技術の乱立を防ぐ。

1. **フォーム管理: React Hook Form (RHF) + Zod の完全採用**
   - 理由: `shadcn/ui` の `<Form>` コンポーネントは RHF と Zod を前提に設計されているため、最もエコシステムとの相性が良い。また、Phase 3 で既に強固な Zod スキーマ（境界防御）を構築済みであり、これをそのままフロントエンドのバリデーションに流用できるため。
2. **データフェッチ・ミューテーション: Next.js Server Actions の採用（TanStack Query は非採用）**
   - 理由: App Routerアーキテクチャにおいては、読み取り（Query）は Server Components で直接インメモリDB（QueryService）から取得し、書き込み（Mutation）は Server Actions 経由で UseCase を叩くのが最もシンプルかつクリーンである。クライアント側にキャッシュ状態を持つ TanStack Query を導入すると、サーバー側の状態と二重管理になりスパゲッティ化の原因となるため、今回は意図的に非採用とする。

### 2.3 コンポーネントの配置ルール（3層構造）
（前項2.1の汎用UI群をベースとし、以下の3層で構築する）

#### ① 汎用UIコンポーネント層 (`src/components/*/`)
前述の通り、ドメイン知識を持たない汎用UI部品群。

#### ② フィーチャー（ドメイン）コンポーネント層 (`src/features/<feature>/components/`)
- **責務**: 特定のドメイン知識を持ち、汎用UIコンポーネント（①）を組み合わせて構築される具体的なUI部品。
- **内容**: `NoteCard`, `PurchaseButton`, `NoteDetail` など。
- **ルール**: データのフェッチ（DBアクセス）は直接行わず、親（③）から Props としてデータ（DTO）を受け取るか、Server Actions を呼び出す役割に徹する。内部に RHF のフォームロジックを持つことは許容される。

#### ③ ルーティング・コントローラー層 (`src/app/`)
- **責務**: Next.js App Router の責務（URLルーティング、Server Componentsによるデータ取得、SEOメタデータの設定など）。
- **内容**: `page.tsx`, `layout.tsx`, `actions.ts`。
- **ルール**: ここには複雑なHTML（JSX）を直接書かず、クエリサービスから取得したデータをフィーチャーコンポーネント（②）に流し込む「Composition Root（結合点）」として振る舞う。

## 3. もたらされる結果 (Consequences)

### メリット
- **カオスの防止**: コピペベースのUIライブラリが複数混在しても、フォルダが分かれているため依存関係が整理され、将来のアップデートや削除が容易になる。
- **データフローの一方通行化**: RHF + Server Actions に絞ることで、「状態がどこにあるかわからない」というフロントエンド特有のスパゲッティ化を根絶できる。

### デメリット・トレードオフ
- 初期セットアップ時に、RHF や Next.js Server Actions の作法（型合わせなど）を厳格に守る必要がある。

## 4. 適用フェーズ
Phase 5 のUI実装以降、すべてのフロントエンド開発においてこのルールを適用する。

### 2.4 ベースコンポーネントの変更とデザイン上書き（Override）のルール
`shadcn/ui` の最大の利点であり弱点でもある「直接ソースコードを編集できる点」によるデザイン崩壊を防ぐため、以下の変更ルールを適用する。

1. **局所的なデザイン変更での大元ファイル編集禁止**
   特定の画面・機能でのみデザインを変えたい場合、`src/components/ui/` 配下の大元コンポーネントを直接編集してはならない。必ず呼び出し側の `className` を用いて Tailwind クラスを上書き（Override）すること。
2. **AIアシスタントの行動制限**
   AIによる自動デザイン修正（Vibe Coding）を行う際、ユーザーから「グローバルなベースコンポーネントを変更して」という明確な指示がない限り、AIは `src/components/ui/` などの汎用コンポーネントを直接編集することを禁止とする。
3. **改変の明記（Modification Tracking）**
   グローバルな仕様変更のために大元ファイルを編集した場合は、ファイル先頭に `// [MODIFIED]: <変更内容>` のコメントを残し、元の `shadcn/ui` のコードから何を変えたかを明記する。
