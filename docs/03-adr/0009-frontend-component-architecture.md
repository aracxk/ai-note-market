# ADR 0009: フロントエンドコンポーネントアーキテクチャとUIライブラリの選定

## 1. 背景と目的 (Context)
Phase 5 にて、堅牢に構築されたDDD（ドメイン層）およびCQRS（クエリ層）に対する最外層として、Next.js App Routerを用いたPresentation（UI）層を実装する。
本プロジェクトの目的は「最適な設計思想の学習」であるため、フロントエンド側においても場当たり的なUI実装を避け、保守性が高く、バックエンドのクリーンアーキテクチャと調和するモダンなコンポーネント配置ルールを策定する必要がある。

## 2. 決定事項 (Decision)

### 2.1 UIライブラリとして `shadcn/ui` を採用する
ブラックボックスなnpmパッケージ（MUI, Chakra UI等）への依存を避け、「所有するUI（Ownership）」の哲学を持つ `shadcn/ui` を採用する。
- ソースコードが直接プロジェクト内に展開されるため、内部実装のカスタマイズが容易であり、将来的なライブラリの仕様変更（ロックイン）に縛られない。
- Tailwind CSSと完全に統合されており、ユーティリティファーストなスタイリングとの相性が良い。

### 2.2 コンポーネントの配置ルール（3層構造）
フロントエンドの関心事を分離するため、以下の3つの階層に分けてコンポーネントを配置する。

#### ① 汎用UIコンポーネント層 (`src/components/ui/`)
- **責務**: ドメイン知識（記事、購入など）を一切持たない、純粋な見た目とインタラクションのみを提供する。
- **内容**: `shadcn/ui` によって生成された Button, Card, Dialog などの部品。
- **ルール**: このディレクトリ内のファイルから、`src/features/` などのドメインロジックをインポートしてはならない。

#### ② フィーチャー（ドメイン）コンポーネント層 (`src/features/<feature>/components/`)
- **責務**: 特定のドメイン知識を持ち、汎用UIコンポーネント（①）を組み合わせて構築される具体的なUI部品。
- **内容**: `NoteCard`, `PurchaseButton`, `NoteDetail` など。
- **ルール**: データのフェッチ（DBアクセス）は直接行わず、親（③）から Props としてデータ（DTO）を受け取るか、Client Componentの場合は Server Actions を呼び出す役割に徹する。

#### ③ ルーティング・コントローラー層 (`src/app/`)
- **責務**: Next.js App Router の責務（URLルーティング、Server Componentsによるデータ取得、SEOメタデータの設定など）。
- **内容**: `page.tsx`, `layout.tsx`, `actions.ts`。
- **ルール**: ここには複雑なHTML（JSX）を直接書かず、クエリサービスから取得したデータをフィーチャーコンポーネント（②）に流し込む「Composition Root（結合点）」として振る舞う。

## 3. もたらされる結果 (Consequences)

### メリット
- **高い凝集度と低い結合度**: 見た目（①）、ドメインUI（②）、ルーティング（③）が分離されるため、どこに何を書くべきか迷わなくなる。
- **アーキテクチャの対称性**: バックエンドの `features/` ディレクトリ構造とフロントエンドのコンポーネント構造が一致し、認知負荷が下がる。

### デメリット・トレードオフ
- **初期セットアップのコスト**: フォルダを細かく分けるため、単純な画面を作る際でも複数のファイルを行き来する必要がある。
- **Propsのバケツリレー**: ③から②へデータを渡す際、型定義（DTO）とPropsの受け渡しが若干冗長になる。

## 4. 適用フェーズ
Phase 5 のUI実装以降、すべてのフロントエンド開発においてこのルールを適用する。
