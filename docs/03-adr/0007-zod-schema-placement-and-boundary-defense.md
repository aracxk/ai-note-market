# ADR 0007: Zod スキーマの配置場所と境界防御（Boundary Defense）方針の決定

- **ステータス**: 承認 (Accepted)
- **決定日**: 2026-09-07
- **意思決定者**: プロダクトオーナー（開発者） & AI アーキテクト

---

## 1. コンテキストと課題 (Context & Problem)

Phase 1 および Phase 2 において、純粋なドメイン層（`domain/`）とユースケース層（`usecases/`）を実装した。
しかし、Web ブラウザのフォーム入力や外部 API リクエストから送信される生データは、TypeScript の型検査が及ばない `unknown` な非型安全データ（泥水）である。

これに対し、以下の設計上の課題が生じた：
1. **ドメイン層の純粋性の担保**: ドメイン層に `zod` などの外部バリデーションライブラリを import せず、純粋な TypeScript を維持しなければならない。
2. **実行時検証（Runtime Validation）の責務**: TypeScript の `interface` はコンパイル時に消滅するため、実行時に不正なデータ形式や型不一致を即座に門前払いする「境界防御」が必要である。
3. **スキーマの配置場所**: Zod によるデータ設計図（スキーマ）をフィーチャー内のどこに配置するのが最も凝集度が高く、Clean Architecture の依存ルールを乱さないか。

---

## 2. 検討した選択肢 (Options Considered)

### 選択肢1: `domain/` 内に Zod スキーマを配置する
- **メリット**: ドメインのバリデーションとスキーマを一元管理できる。
- **デメリット**: ドメイン層が外部 npm パッケージ（Zod）に強く依存し、A-1規約（外部依存ゼロ・純粋性）に真っ向から違反する。

### 選択肢2: `usecases/` 配下に DTO と同居させる
- **メリット**: ユースケースの入力（Input DTO）の定義場所にスキーマを置くため、`z.infer` で DTO を直接生成できる。
- **デメリット**: ユースケース層が特定のバリデーションライブラリ（Zod）の存在を知ることになり、手順の記述という責務から外れる。

### 選択肢3: `schemas/` をフィーチャー直下に独立配置する（採用）
```text
src/features/<feature>/
├── domain/            # 純粋なビジネスルール（Zod 非依存）
├── usecases/          # ユースケース手順 ＆ ポート（純粋な TypeScript）
├── infrastructure/    # リポジトリ等の具象
└── schemas/           # ★外部入力の境界防御（Zod スキーマと型導出）
```
- **メリット**:
  1. ドメイン層およびユースケース層の純粋性を 100% 保持できる。
  2. 外部境界（将来の Next.js Server Actions や API Routes）から直接参照し、コントローラ層での門前払いフィルターとして即座に活用できる。
  3. `z.infer` により TypeScript の Input DTO 型を自動生成し、手書きによる二重メンテを根絶できる。
  4. 将来 Swagger / OpenAPI（`zod-to-openapi`）を導入する際、この `schemas/` を単一の信頼できる情報源（Single Source of Truth）としてそのまま再利用できる。
- **デメリット**: ディレクトリが1つ増える（ただし明確な責務境界として許容範囲）。

---

## 3. 決定事項 (Decision)

**選択肢3（`src/features/<feature>/schemas/` への独立配置）をプロジェクト標準として採用する。**

### 運用ルール:
1. **境界防御の徹底**: 外部から入ってくるリクエストデータは、必ず `schemas/` の Zod スキーマで `safeParse` してから UseCase に引き渡す。
2. **型の自動導出**: DTO 型は手動で `interface` を書かず、`export type XxxInput = z.infer<typeof xxxSchema>;` でスキーマから自動導出する。
3. **ドメイン層への持ち込み禁止**: `src/**/domain/` 配下のファイルからは、いかなる場合も `schemas/` や `zod` を import してはならない。

---

## 4. 得られる効果とトレードオフ (Consequences)

### ポジティブな影響
- **ドメイン純粋性の完全保護**: 不正な形式のデータはドメイン層に到達する前に境界で遮断される。
- **UI に親切なエラー表現**: フィールド単位のバリデーションエラーを画面に返しやすくなる。
- **将来の Swagger 連携の容易性**: スキーマ駆動の土台が完成し、API ドキュメント化のコストが最小化される。

### トレードオフと留意点
- ドメイン層のバリデーション（例: タイトルの最小文字数）と、Zod スキーマの制約値（`.min(5)`）が同期している必要がある。定数の共有（`DOMAIN_CONSTRAINTS` など）によって乖離を防ぐ。
