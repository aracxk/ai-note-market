# ADR 0002: デプロイ基盤としての Vercel 採用および導入計画

- **ステータス**: 承認済 (Accepted)
- **日付**: 2026-08-23
- **意思決定者**: ユーザー & Antigravity (AI)

---

## 1. コンテキスト（背景と課題）

本プロジェクトは設計思想（DDD、クリーンアーキテクチャ、フィーチャーデザイン等）の学習を主目的としているが、実装した成果物を Web 上で迅速に確認・共有できるホスティング基盤が必要とされた。
また、将来的な学習のテンポを落とさないため、インフラの保守管理コストを最小限に抑えつつ、Next.js 14（App Router / Server Actions）の性能を最大限に引き出せる環境が求められた。

---

## 2. 決定事項 (Decision)

以下の通り、デプロイ基盤および導入タイミングを決定する：

1. **ホスティング環境として Vercel を採用**:
   - Next.js の公式最適化環境であり、ゼロコンフィグでのプレビュー環境提供、Server Actions のネイティブ実行が可能であるため。
2. **導入タイミング**:
   - **Phase 5（Next.js App Router による UI プレゼンテーション層の実装時）** に Vercel との連携・デプロイを行う。
   - Phase 1〜4（ドメイン層、ユースケース層、Zodバリデーション、フィーチャー構造化）までは、Vitest による高速な単体テストを中心にロジックを構築し、画面ができあがった段階で Web 公開する。
3. **アーキテクチャ上の留意事項（サーバーレス設計）**:
   - Vercel はステートレスな実行環境であるため、メモリ永続化に依存せず、Repository インターフェースを通じて将来的な外部DB（Vercel Postgres, Neon, Supabase 等）への差し替えが容易なクリーンアーキテクチャの構造を維持する。

---

## 3. 結果・影響 (Consequences)

### メリット (Positive)
- GitHub へのプッシュと連動した自動プレビュー環境が利用可能となり、Playwright E2E テストの対象としても活用できる。
- インフラ管理に時間を奪われず、純粋なドメイン設計・アーキテクチャの学習に集中できる。

### トレードオフ・デメリット (Negative / Cost)
- バックエンドを Go 言語等で別立てにする場合、Vercel Serverless Functions (Go) を利用するか、外部コンテナサービス（Fly.io / Render 等）とのハイブリッド構成を検討する必要がある（Phase 7 にて比較検討）。
