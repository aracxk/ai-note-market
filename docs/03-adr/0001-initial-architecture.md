# ADR 0001: 初期アーキテクチャおよび設計方針の採択

- **ステータス**: 承認済 (Accepted)
- **日付**: 2026-08-23
- **意思決定者**: ユーザー & Antigravity (AI)

---

## 1. コンテキスト（背景と課題）

本プロジェクトは、設計思想（DDD、クリーンアーキテクチャ、フィーチャーデザイン等）を段階的に深く学ぶためのプロジェクトである。
題材として「AI × note アイディア販売所（AI-Note Market）」を採用し、実践的なビジネスルールを扱う。
学習の質を高めるため、以下の要件を満たす設計アーキテクチャが必要とされた：

1. ビジネスルールがフレームワーク（Next.js等）やDBに汚染されず、純粋な単体テストが高速に実行できること。
2. レイヤーごとの責務（ドメイン、ユースケース、インフラ、UI）が明確で、依存性の逆転（DIP）を体感できること。
3. AIが勝手に実装を進めず、対話的・教育的な伴走を実現すること。

---

## 2. 決定事項 (Decision)

以下のアーキテクチャ・スタックを採択する：

1. **ドメイン層の完全分離 (DDD)**:
   - ビジネスルールはすべて `domain/` 内の Value Object, Entity, Aggregate に集約する。
   - 外部ライブラリへの依存を排除し、純粋なTypeScriptで記述する。
2. **クリーンアーキテクチャによる依存性の逆転 (DIP)**:
   - UseCase 層は Repository Interface に依存し、具象実装（InMemory / DB）は Infrastructure 層に配置する。
3. **フィーチャーベースのディレクトリ構成**:
   - `src/features/note/`, `src/features/purchase/` のように機能単位で凝集させる。
4. **AI制御規範の制定 (`agent.md`)**:
   - 1ステップごとの解説・合意形成・テスト・ドキュメント化のサイクルを厳守する。

---

## 3. 結果・影響 (Consequences)

### メリット (Positive)
- ビジネスルールの単体テストがミリ秒単位で高速に動作し、フレームワークのバージョンアップやDB変更の影響を受けない。
- 設計の意図とトレードオフが `docs/` に体系的に蓄積されるため、学習効果が最大化される。

### トレードオフ・デメリット (Negative / Cost)
- 小規模なCRUDアプリに比べると、ボイラープレートコード（Value Object定義、Repositoryインターフェース、DTO変換）の量が増える。
- → 今回は「学習」が主目的であるため、このオーバーヘッド自体が設計の価値を理解するための教材となる。
