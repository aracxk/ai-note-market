# ADR 0005: 記事カテゴリの分類軸再設計（ツール依存から目的領域×成果物形式への普遍化）

- **ステータス**: 承認済 (Accepted)
- **日付**: 2026-08-23
- **意思決定者**: ユーザー & Antigravity (AI)

---

## 1. コンテキスト（背景と課題）

当初のカテゴリ設計では、大カテゴリを「AIツール名（`CLAUDE`, `CURSOR` 等）」、小カテゴリを「特定ツールの形式（`SKILLS`, `CURSOR_RULES` 等）」としていた。
しかし、以下の課題が特定された：

1. **目的・用途の不透明さ**: 購入者が「プログラミング用なのか、マーケティング用なのか、デザイン用なのか」という業務目的から記事を探せない。
2. **ツールの変化に対する脆弱性**: AIツールの栄枯盛衰（新ツール登場や仕様変更）のたびに、ドメインの基幹カテゴリ定義を変更・デプロイする必要が生じる。
3. **複数ツール横断記事の表現不能**: 1つの記事で「Claude と Cursor を連携させるノウハウ」を扱った際に、単一のツール大カテゴリに押し込めることが不自然となる。

---

## 2. 決定事項 (Decision)

コンテンツ販売プラットフォーム（note, Zenn等）の普遍的な分類モデルに基づき、カテゴリの概念軸を以下の通り再設計する：

1. **大カテゴリ（`MajorCategory`）**: **「目的・業務領域」** を表す。
   - `ENGINEERING`（開発・プログラミング）
   - `MARKETING`（マーケティング・SNS運用）
   - `DESIGN`（デザイン・画像生成）
   - `WRITING`（ライティング・執筆）
   - `BUSINESS`（業務効率化・バックオフィス）
   - `OTHER`（その他）
2. **小カテゴリ（`MinorCategory`）**: **「成果物の形式・アセット種別」** を表す。
   - `PROMPT`（プロンプト・指示文）
   - `RULES_CONFIG`（設定ファイル・ルール定義）
   - `SKILLS_EXTENSION`（スキル・エージェント・カスタム拡張）
   - `SOURCE_CODE`（ソースコード・自動化スクリプト）
   - `WORKFLOW_GUIDE`（ワークフロー・体系的ノウハウ）
   - `OTHER`（その他）
3. **個別ツール名（Claude, Cursor, ChatGPT等）の扱い**:
   - カテゴリではなく、将来的に記事集約の「タグ（`tags: string[]`）」として複数付与可能な設計とする。

---

## 3. 結果・影響 (Consequences)

### メリット (Positive)
- 10年後も陳腐化しない普遍的で直感的なドメインモデルが確立された。
- 購入者が「自分の業務（開発/マーケ等）」と「欲しい形式（プロンプト/コード等）」から自然に記事を検索・発見できるようになった。
- ツール名に縛られず、あらゆるAI活用ノウハウを柔軟に収容可能となった。

### トレードオフ・デメリット (Negative / Cost)
- カテゴリの型定義および単体テストの全ケースを新軸に更新する必要がある。

---

## 4. 将来の拡張指針（Future Considerations: 階層増加時の対応）

現状は YAGNI（今必要ない複雑さは持ち込まない）の原則に従い、UIおよびドメインが最もシンプルに扱える **「2階層（大×小）」** で設計している。
将来的に中カテゴリの追加（3階層）や、ツリー構造（N階層）への拡張が必要となった場合は、以下の設計パターンへ移行する：

1. **パス結合キー方式（Path Key）への移行**:
   - キャッシュキーを `path.join("/")`（例: `"ENGINEERING/AI_CODING/RULES_CONFIG"`）とする可変長パス方式を採用することで、Flyweight キャッシュの仕組みをそのまま維持しつつ任意階層を収容可能とする。
2. **Composite パターン（ツリー構造）の採用**:
   - `Category` が自己参照（`parent: Category | null`）を持つ構造へリファクタリングする。
