# ADR 0008: 読み取り専用モデル（QueryService）としての CQRS パターンの採用

## 日付
2026-09-11

## ステータス
Accepted

## 背景と課題
記事の一覧（トップページ）やマイページの購入履歴一覧を表示する際、これまでの `Repository` を使って `Note` や `Purchase` などの集約（エンティティ）を再構築（復元）してから画面に渡すと、以下の問題が発生します。

1. **パフォーマンスとメモリの浪費**: 画面には「タイトル」と「価格」しか必要ないのに、本文（Content）などの重いデータをすべてメモリにロードしてエンティティを作ってしまう。
2. **N+1問題の発生**: 購入履歴から「購入した記事のタイトル」を表示する際、Purchase リポジトリで取得した後に Note リポジトリをループで叩くことになり、N+1クエリが発生する。
3. **副作用の危険性**: 画面表示のためだけにエンティティをロードすると、誤ってエンティティのメソッド（書き込み処理）を呼び出して状態を変更してしまうリスクがある。

## 決定事項
「書き込み用のドメインモデル（Repository）」と「読み取り用のクエリモデル（QueryService）」を明確に分離する **CQRS (Command Query Responsibility Segregation)** パターンを採用します。

1. **QueryServiceの導入**:
   - 画面用のデータ取得専用のインターフェースとして `QueryService` を定義する。
   - インターフェースの定義は `src/features/<feature>/queries/` に配置する。
2. **DTO (Data Transfer Object) の利用**:
   - `QueryService` の戻り値は、ドメインエンティティではなく、プリミティブな型のみを持つ `readonly` な DTO とする。
3. **インフラ層での直接JOIN**:
   - 実装（`infrastructure`）側では、ORマッパーなどを駆使してデータベース側で JOIN などを効率的に行い、直接 DTO を生成して返す（現在はインメモリで疑似的にJOINしている）。

## 影響
- **ポジティブ**:
  - 画面表示のためのクエリが劇的に高速化し、メモリ使用量も減る。
  - `Repository` は「ドメインの書き込み・整合性維持」のみに集中でき、インターフェースがシンプルになる。
- **ネガティブ**:
  - `Repository` と `QueryService` の2種類のインターフェースと実装が存在するため、ファイル数が増える。
