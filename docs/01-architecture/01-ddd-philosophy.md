# ドメイン駆動設計（DDD）の思想と基礎概念

## 1. なぜドメイン駆動設計（DDD）なのか？

一般的なWeb開発では、データベースのテーブル定義（スキーマ）から考え始め、画面（UI）やCRUD処理を直接書きがちです。
しかし、このアプローチ（データ駆動設計）には以下の問題が生じます：

- **ロジックの散乱**: 「有料記事の価格は100円以上」「著者は自分の記事を買えない」といった重要なビジネスルールが、UIコンポーネント、APIルート、DBバリデーションなどに分散して重複する。
- **貧血ドメインモデル**: クラスや型が単なるプロパティの入れ物（Getter/Setterのみ）になり、実際のルールを誰が保証しているのか分からなくなる。
- **仕様変更に弱い**: 「価格上限が50,000円から100,000円に変更」となった際、コード中のあちこちの `if (price > 50000)` を探して修正する必要がある。

**DDD（Domain-Driven Design）** では、システムの中心に**「純粋なビジネスのルールと概念（ドメインモデル）」**を置き、UIやDBといった外部の都合から完全に隔離します。

---

## 2. コア概念の比較

| 概念 | 特徴 | 例（AI-Note Market） |
| :--- | :--- | :--- |
| **値オブジェクト (Value Object)** | ・一意なIDを持たない<br>・「値」そのもので同一性を判定<br>・**完全イミュータブル（不変）**<br>・自己バリデーションを持つ | `Price`（価格）, `NoteTitle`（タイトル）, `Category`（大分類×小分類）, `UserId` |
| **エンティティ (Entity)** | ・**一意な識別子（ID）** を持つ<br>・属性が変わっても同じものとして追跡される<br>・ライフサイクル（状態遷移）を持つ | `Note`（記事：下書き→公開→停止）, `User`（ユーザー） |
| **集約 (Aggregate)** | ・強い一貫性を保つべきエンティティと値オブジェクトのまとまり<br>・外部からは集約ルート（Aggregate Root）経由でのみ操作可能 | `Note` 集約, `Purchase` 集約 |
| **ドメインサービス (Domain Service)** | ・単一のエンティティや値オブジェクトに収まらない複数エンティティを跨ぐルール | 「記事購入可否チェック（NoteとPurchaseの整合性確認）」 |

## 3. 値オブジェクト（Value Object）の真価

たとえば、「価格」を単なる `number`（プリミティブ型）で扱うとどうなるでしょうか？

```typescript
// ❌ プリミティブ型（アンチパターン）
function createNote(title: string, price: number) {
  // price に -500 や 999999999 が渡されてもコンパイルは通ってしまう！
  // 呼び出し側の至る所で毎回 if (price >= 100 && price <= 100000) と書く羽目になる
}
```

```typescript
// ⭕ Value Object（堅牢な設計）
class Price {
  private constructor(private readonly value: number) {}

  public static create(value: number): Price {
    if (value !== 0 && (value < 100 || value > 100000)) {
      throw new Error("価格は0円（無料）または100円〜100,000円の範囲で指定してください。");
    }
    return new Price(value);
  }

  public isFree(): boolean {
    return this.value === 0;
  }

  public get amount(): number {
    return this.value;
  }
}
```

これによって：
1. `Price` 型を受け取る関数は、**「渡された時点で必ず正しい価格である」ことが型レベルで保証される**ため、内部での二重チェックが不要になります。
2. 価格に関するルール変更（例: 上限を10万円にする）が発生しても、`Price` クラスの1箇所を修正するだけでシステム全体に適用されます。
