# テスト戦略 (Testing Strategy) - AI駆動開発時代への最適化

本プロジェクトにおけるテスト戦略は、単なるWebアプリケーションの品質担保にとどまらず、**「AIエージェント（Antigravity等）が自律的にコードを生成・保守する際の生産性を最大化すること」** を最重要目的として設計されている。

従来の「テストピラミッド」を捨て、現代の Next.js (App Router) と AI駆動開発（Agentic Coding）に最適化された**「二極化テスト戦略（Bipolar Testing Strategy / Testing Trophy）」**を採用する。

---

## 1. なぜ「中間のテスト」を捨てるのか？（AI駆動視点での課題）

従来のReact開発では、React Testing Library (RTL) 等を用いた「UIコンポーネント単体のテスト（中間のテスト）」が推奨されていた。しかし、本プロジェクトではこれを**完全非推奨（スキップ）**とする。

### 【理由】AIによる「モック地獄」とハルシネーションの回避
Next.js App Router では、UIコンポーネントがサーバー処理（Server Actions）やルーティングと密結合しやすい。これをRTLでテストするには、フレームワークの内部機構を精巧に「モック（偽装）」する必要がある。
AIエージェントは、この「特定のフレームワークの複雑な内部モック」を書くのが非常に苦手であり、バージョンアップ等でAPIが変わるとすぐにハルシネーション（誤ったコード生成）を起こし、**「少しUIを変えただけでAIがテストを直せなくなる（脆いテスト）」**という問題が多発するためである。

---


## 2. AI時代のテスト階層（二極化戦略）

モック地獄を避けるため、テストの対象を「完全に純粋なロジック」と「完全にリアルなユーザー行動」の両極端に振り分ける。

### ① 【最下層】純粋なロジックの徹底保護 (Unit Testing)
- **ツール**: Vitest
- **AIとの相性**: ⭐️⭐️⭐️⭐️⭐️

#### 📂 厳格なモック境界線（Mock Boundary）の具体化ルール
形骸化（意味のない嘘のテスト）を防ぐため、「何をモックしてよくて、何をしてはいけないのか」を具体的に定義する。

| カテゴリ | 対象レイヤー（例） | モック (spyOn等) の可否 | 具体的な手法・理由 |
| :--- | :--- | :--- | :--- |
| **A. 内部状態（自社DB）** | `Repository`, `QueryService` | **❌ 完全禁止** | 本物のDBと同じ振る舞いをする **Fake（InMemoryアダプター）** を必ず作成・使用する。UseCaseが「本当にデータを更新できたか」という状態（State）を検証するため、リファクタリングに極めて強く、形骸化しない。 |
| **B. 外部システム（副作用）** | `PaymentService` (Stripe), `EmailService` | **✅ 許容（条件付き）** | 自社でコントロールできない外部APIは、単体テストで本物と通信できないため、`vi.spyOn`等によるモック（Stub）注入を許容する。「通信エラー」「カード決済失敗」などの異常系を擬似的に起こし、UseCaseのエラーハンドリングをテストするために用いる。 |
| **C. システムコンテキスト** | 日時(`Date`), 乱数(`UUID`) | **✅ 固定化必須** | テストの実行結果を決定論的（毎回同じ結果）にするため、`vi.setSystemTime`等による時刻や乱数の固定化（Stubbing）は必須要件とする。 |

#### 📂 フォルダ単位の明確なカバレッジ強制ルール

属人化やAIによる「テストの書き漏れ・ブレ」を完全に防ぐため、**「テスト対象（100%）」と「テスト除外（0%）」をフォルダ単位で物理的に分断し、CIでカバレッジ100%を強制する（ホワイトリスト方式）**。

**【✅ テスト必須フォルダ（Vitest カバレッジ 100% 強制）】**
モックを使わずにローカルで安定・高速に実行できるバックエンド領域。
* `src/features/*/domain/` : ビジネスルール（エンティティ、値オブジェクト）
* `src/features/*/usecases/` : アプリケーションの進行ロジック
* `src/features/*/queries/` : 読み取り専用の抽出・マスキングロジック（セキュリティ関門）
* `src/features/*/infrastructure/` : 自社データベース（Prisma等）の操作（※モック禁止、テスト用DBで結合テスト）

**【❌ テスト除外フォルダ（Vitest 対象外 ➔ Playwrightで担保）】**
外部ネットワークやフレームワークに依存し、単体テストを書くと「モック地獄（脆いテスト）」になる領域。
* `src/app/` : Next.js ルーティング
* `src/components/` , `src/features/*/components/` : UI・React層
* `src/features/*/actions/` : Server Actions（CookieやrevalidatePath依存）
* `src/features/*/external/` (新設) : StripeやSendGridなど、自社でコントロールできない外部API通信の隔離先

### ② 【最上層】ユーザーシナリオの貫通 (End-to-End Testing)
- **ツール**: Playwright
- **対象**: ブラウザを通じた実際のユーザー行動（ログイン、決済、画面遷移など）
- **AIとの相性**: ⭐️⭐️⭐️⭐️⭐️
- **設計思想**: 内部実装を一切モックせず、本物のブラウザを自動操縦する。AIは「内部の複雑な仕組み」を理解する必要がなく、「購入ボタンを押す」「テキストが表示される」という直感的な仕様書から高精度なスクリプトを生成できる。
- **自己修復 (Self-Healing)**: かつてE2Eテストは「ボタンの名前が変わっただけで壊れる（保守コストが高い）」のが弱点だったが、現在ではテストが落ちた際、AIエージェントにエラーログとHTMLを渡せば**瞬時にテストコードを自己修復**できるため、最大の弱点が克服されている。
- **目標**: 主要なハッピーパス（コアユースケース）の完全網羅

### ⓪ 【土台】静的解析の強制 (Static Analysis)
- **ツール**: TypeScript, Biome
- **対象**: プロジェクト全体
- **設計思想**: AIが生成したコードの「型違反」や「未使用変数」をコミット前に（Husky経由で）機械的に弾き、人間のレビューコストを削減する。

## 3. 開発・運用ワークフロー

1. **仕様定義**: 人間（ユーザー）が「業務ルール（DDD）」と「ユーザーシナリオ（E2E）」を自然言語で定義する。
2. **実装・テスト生成**: AIエージェントが、純粋なドメイン層（Vitest）と、UIを貫通するシナリオ（Playwright）のテストを生成し、それを満たす実装を行う。
3. **継続的保守**: UI変更によってPlaywrightのテストが破損した場合、人間が手動で直すのではなく、エラーログをAIに渡して自己修復（Self-Healing）させるフローを標準とする。

## 4. E2Eテストの検証結果・証跡（Trace）管理
PlaywrightによるE2Eテストは、単なる合否の判定にとどまらず、デバッグや品質保証のための「視覚的な証跡」を自動で残す設計とする。

### 4.1 保存されるアーティファクト（証跡）
Playwright実行時に生成される以下のファイル群は、Gitの管理対象外（`.gitignore`）とし、ローカルまたはCI環境上にのみ保存する。
- **HTMLレポート (`playwright-report/`)**: テスト全体の合否、実行時間、各ステップのサマリーを視覚化する静的ファイル。
- **テスト結果・トレース (`test-results/`)**: 失敗時のスクリーンショット、動画、およびTraceファイルが保存される。

### 4.2 Trace Viewer（タイムマシンデバッグ）の徹底
- **ルール**: CI（GitHub Actions等）環境において、テストがリトライしても失敗した場合は**必ずTrace機能（`trace: 'on-first-retry'` または `retain-on-failure`）を有効化**し、Traceファイル（`.zip`）をCIのアーティファクトとして保存する。
- **運用**: テスト失敗時、開発者は手元で再現を試みる前に、まずこのTraceファイルをダウンロードしてPlaywright Trace Viewer（`npx playwright show-trace`）で開くこと。ミリ秒単位のDOMの状態、ネットワークリクエスト、コンソールログを「タイムマシン」のように巻き戻して確認し、失敗原因を特定する。
