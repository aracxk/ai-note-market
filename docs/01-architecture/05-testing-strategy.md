# テスト設計戦略：テストピラミッドとドメイン単体テストの原則

- **カテゴリ**: アーキテクチャ理論 (`docs/01-architecture/`)
- **テーマ**: DDD・クリーンアーキテクチャにおけるテスト設計の考え方とベストプラクティス

---

## 1. テストピラミッド（テストの階層構造）

ソフトウェアテストは、以下の3層で役割を分担します。

```text
       / \
      / E2E \       [ Playwright ] ユーザー視点の画面シナリオ（少数・高コスト）
     /-------\
    /  結合   \     [ Integration ] ユースケース＋DB連携・API通信（中規模）
   /-----------\
  /   単体テスト  \  [ Vitest / Unit ] ドメインルール・不変条件（大量・超高速・低コスト）
 /---------------\
```

| 層 | 対象 | ツール | 特徴 |
| :--- | :--- | :--- | :--- |
| **単体テスト (Unit)** | Value Object, Entity, Domain Service | Vitest | ミリ秒単位で実行。外部依存（DB/Network/UI）なし。網羅性を追求。 |
| **結合テスト (Integration)** | UseCase, Repository 具象 | Vitest | インメモリDBやモックを使用し、手順とデータの流れを検証。 |
| **E2Eテスト (End-to-End)** | 画面操作からサーバー全体 | Playwright | 実際のブラウザを動かし、主要なユーザージャーニーを検証。 |

---

## 2. ドメイン層の単体テストにおける鉄則

ドメイン層（Value Object や Entity）の単体テストは、以下の原則を厳守します。

### ① 外部依存ゼロ（No External Dependencies）
- データベース、Next.js、HTTP通信などのモック（Mock）やスタブを一切持ち込まない。
- 純粋なクラスのインスタンス化とメソッド呼び出しのみで完結させる。
- **効果**: テストが並列で数千件走っても数秒以内で完了し、開発テンポ（Feedback Loop）が最速になる。

### ② 不変条件（ビジネスルール）の境界値を徹底的に検証
- **等価分割（Equivalence Partitioning）**:
  - 有効なグループ（代表値: 1,000円など）
  - 無効なグループ（代表値: -100円、50円、100,000円など）
- **境界値分析（Boundary Value Analysis）**:
  - 境界のキワ（0円、99円、100円、100,000円、100,001円）を必ずテストケースに含める。

## 3. テストコードの構造化：AAAパターン

すべてのテストケースは、**Arrange（準備） / Act（実行） / Assert（検証）** の3ステップで統一して記述します。

```typescript
it("0円（無料）の価格オブジェクトを正常に生成できること", () => {
  // 1. Arrange (準備): 入力値や前提条件を整える
  const inputAmount = 0;

  // 2. Act (実行): テスト対象のメソッドを呼び出す
  const result = Price.create(inputAmount);

  // 3. Assert (検証): 期待通りの結果（値、型、ステータス）になっているか検証する
  expect(result.success).toBe(true);
  if (result.success) {
    expect(result.value.amount).toBe(0);
    expect(result.value.isFree()).toBe(true);
  }
});
```

## 4. テストケースの命名規約

- テスト名は「実装の詳細」ではなく、**「仕様（ビジネスルール）」** として読める日本語で記述する。
- 形式: **「〜の場合、〜であること」** / **「〜できること」**

### 良い例
- `it("下限値（100円）の価格オブジェクトを正常に生成できること")`
- `it("100,001円以上（上限超過）を指定した場合はエラーになること")`

### 悪い例
- `it("create test 1")`
- `it("Price.create should return false when value is 50")`

## 5. ローカルテストとCI/CDの役割分担 (ビルドチェックの考え方)

フロントエンド開発（特にNext.jsのようなビルドステップを伴うフレームワーク）においては、テストの実行タイミングと開発体験（DX）のバランスが極めて重要です。

### ① Husky (ローカルのコミット前フック)
- **原則**: **超高速な検査のみに限定する。**
- **対象**: `npm run typecheck` (TypeScriptの型検査) および `biome check` (Lint・フォーマット)。
- **理由**: これらは数ミリ秒〜数秒で完了し、開発のテンポを落とさずに最低限の構文エラーや型エラーを防ぐため。
- **禁止事項**: `npm run build` のような完了までに数十秒かかる重い処理を Husky に組み込んではならない。開発者のコミットを毎回ブロックし、DXを著しく損なうアンチパターンである。

### ② CI/CD (GitHub Actions等)
- **原則**: **最終的な防波堤として重い処理をすべて引き受ける。**
- **対象**: `npm run build` (Next.jsビルドによるCSSパースやWebpackのチェック)、およびフルテストスイート (`npm run coverage`)。
- **理由**: ローカルの開発速度を犠牲にすることなく、メインブランチに壊れたコード（CSSビルドエラーなど）がマージされるのをサーバー側で確実に防ぐため。

### ③ AIによる自律チェックの指針
AIエージェント（Antigravity等）が品質の自己診断を行う際も、人間の開発者と同じテンポ感を維持するため、毎回のターンで重いビルドは行わない。
ただし、「UIフレームワークの入れ替え」「TailwindやNext.jsの設定ファイル変更」といった**ビルドプロセス自体に影響を与える基盤変更を行った際のみ、例外として `npm run build` を手動で実行し、安全を確認する**こと。
