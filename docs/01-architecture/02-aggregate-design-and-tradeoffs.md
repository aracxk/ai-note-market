# 集約設計の原則・崩壊パターンとトレードオフ (Aggregate Design & Trade-offs)

- **カテゴリ**: アーキテクチャ理論 (`docs/01-architecture/`)
- **テーマ**: DDDにおける集約の境界設定、4大崩壊パターン、直面する課題と解決策（CQRS・UseCase協調）

---

## 1. 集約（Aggregate）の設計原則

集約とは、「強い整合性を保つべきエンティティと値オブジェクトを1つの境界線（カプセル）で囲ったまとまり」である。

1. **集約ルート経由の操作**:
   - 外部（UseCase/UI）は内部の部品を直接操作できず、必ず集約ルート（`Note`, `Purchase`）の業務メソッド（`publish()`, `create()` 等）を経由する。
2. **集約間のID参照原則（疎結合）**:
   - 集約が他の集約を参照する際は、オブジェクト実体を持たず、**必ず一意なID（`NoteId`, `UserId` 等）のみを保持する**。
   - これにより、メモリ消費の爆発防止、ロック競合の回避、独立したスケーラビリティを担保する。

## 2. 実務で現場が崩壊する「4大アンチパターン」

```text
┌─────────────────────────────────────────────────────────────┐
│ 1. 集約の肥大化（God Aggregate）                            │
│    ・レビュー、コメント、いいねを全部 Note に突っ込む       │
│    ➔ 対策: 別集約（Review, Like）に明確に切り出す           │
├─────────────────────────────────────────────────────────────┤
│ 2. 集約間の直接参照（境界線の破壊）                         │
│    ・Purchase の中に Note 実体を持たせる                    │
│    ➔ 対策: 必ず NoteId（ID値）による参照に徹する             │
├─────────────────────────────────────────────────────────────┤
│ 3. ドメイン層の汚染（外部都合の逆流）                       │
│    ・UIの日付表示形式やStripe固有IDをドメインに書く         │
│    ➔ 対策: UI都合はPresentation層、外部APIはインフラ層へ    │
├─────────────────────────────────────────────────────────────┤
│ 4. 安易な Setter の追加（貧血ドメインへの逆戻り）           │
│    ・note.status = "PUBLISHED" と直接代入させる             │
│    ➔ 対策: 業務メソッド（publish()）経由でのみ状態変更を許す│
└─────────────────────────────────────────────────────────────┘
```

## 3. この設計を採用したことで直面する「3つの課題」と「解決策」

集約を小さく疎結合に保つ設計には多くのメリットがあるが、以下のトレードオフ（今後の課題）が生じる。これらに対しては確立された解決パターンを適用する。

### 課題①：一覧画面・マイページでのデータ結合（JOIN）の手間
- **課題**: `Note` と `Purchase` が分離しているため、「購入日時 ＋ 記事タイトル ＋ 著者名」を一覧表示する際にN+1問題や複数取得の手間が生じる。
- **解決策（CQRS: 読み書きの分離）**:
  - **更新（コマンド）**: 今回作成した `Note` / `Purchase` 集約で厳格にビジネスルールを守る。
  - **参照（クエリ）**: 集約を通さず、SQL（Prisma/Drizzle/生のJOIN）で画面専用の DTO（`PurchaseHistoryDTO`）を一発で高速取得する。

### 課題②：複数集約をまたぐ整合性の協調
- **課題**: 「記事購入時に、購入記録作成と同時に著者のウォレット残高を加算したい」など、複数集約を連動させる必要がある。
- **解決策（UseCase層でのオーケストレーション / ドメインイベント）**:
  - Phase 2 で実装する **UseCase（アプリケーションサービス）** が、オーケストラの指揮者のように複数の集約を順番に呼び出してトランザクションをまとめる。
  - 将来の大規模化時は、ドメインイベント（`NotePurchasedEvent`）による非同期連携（最終的一貫性）へ移行する。

### 課題③：ファイル数・ボイラープレートの増加（初期コスト）
- **課題**: 単純なCRUDに比べて、Value Object や Entity のファイル数が増える。
- **解決策**:
  - 薄い基底クラス（`ValueObject`, `Entity<ID>`）を活用して重複コードを最小化する。
  - アプリ完成後の「バグ調査時間ゼロ」「安全な仕様変更」という圧倒的な保守性（ROI）によって初期コストを回収する。
